\doxysubsection{Detailed Description}
Function overloading is how DITS utilizes call-\/back. 

Implementer must overload all of these functions correctly to tie the protocol engine to the hardware it runs on.

Notification that the DIT table has changed due to received network data. 

This callback is invoked when the DIT table is modified as a result of packet processing, such as discovering a new remote node or synchronizing due to a detected DIT table mismatch. All internal storage updates are completed before this function is called. \begin{DoxyNote}{Note}
DIT table change initiated by the implementer does not trigger this callback.

\begin{DoxyReturn}{Returns}
true if transmission may proceed or false if UART or Radio is busy.
\end{DoxyReturn}
Typical flow considerations:\+
\begin{DoxyItemize}
\item UART buffer availability (e.\+g., Serial.\+available\+For\+Write()).
\item RF radio-\/ready signals (e.\+g., AUX pin on E22).
\item Leading radio specific header requirments (e.\+g. address, channel, etc...) \begin{DoxyImportant}{Important}
It is the implementers responsibility to send the radio its appropriate header just before returning true. The protocol engine will always provide the destination address of the packet by passing it to {\ttfamily \+\_\+\+To\+RFAddr} on every call. Address 0x\+FFFF will be passed if there is no destination address. This allows radio usage flexibility. 
\end{DoxyImportant}
\begin{DoxyNote}{Note}
If Radio\+Pkt\+Max\+Bytes is known to always be less than the UART buffer depth, the implementer may choose to wait until enough space is available in the UART buffer to signal ready. Otherwise, simply checking that the UART buffer is not full is sufficient. 
\end{DoxyNote}
